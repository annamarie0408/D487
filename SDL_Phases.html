Phase-by-Phase Detail

Click any phase to expand. Pay attention to the competency line — it tells you what the phase is actually testing you on, not just what happens in it.

A1 Security Assessment Phase

Competency: Assessing software requirements and risks

Success Factors

  • Accuracy of planned SDL activities
  • Product risk profile understanding
  • Accurate threat profile
  • Coverage of regulations/compliance
  • Security objectives coverage

Deliverables

  • Product risk profile
  • SDL project outline
  • Applicable laws and regulations
  • Threat profile
  • Certification requirements
  • Third-party software list
  • Metrics template
A2 Architecture Phase

Competency: Examining security principles within the SDLC

Success Factors

  • Business requirements and risks identified (CIA)
  • Effective threat modeling
  • Architectural threat analysis
  • Risk mitigation strategy
  • DFD accuracy

Deliverables

  • Business requirements
  • Threat modeling artifacts (DFDs, elements, threats)
  • Architecture threat analysis
  • Risk mitigation plan
  • Policy compliance analysis
This is where threat modeling starts — the DFD and initial STRIDE/DREAD pass happen here. A3 doesn't create a new one, it updates this one.
A3 Design & Development Phase

Competency: Evaluating the software security test plan

Success Factors

  • Comprehensive security test plan
  • Effective threat modeling (continued)
  • Design security analysis
  • Privacy implementation assessment
  • Policy compliance review updates

Deliverables

  • Updated threat modeling artifacts
  • Design security review
  • Security test plans
  • Updated policy compliance analysis
  • Privacy implementation assessment results
Notice the verbs: A2 creates, A3 updates. A3 also introduces the test plan — not execution yet. Execution is A4.
A4 Readiness Phase

Competency: Evaluating the effectiveness of software testing

Success Factors

  • Security test case execution
  • Security testing completion
  • Privacy validation and remediation
  • Policy compliance review

Deliverables

  • Security test execution report
  • Updated policy compliance analysis
  • Privacy compliance report
  • Security testing reports
  • Remediation report
A4 is where the plan written in A3 gets run. If a question mentions fuzzing, dynamic analysis, or "test case execution," it's A4.
A5 Ship Phase

Final release preparation

Success Factors

  • Final policy compliance analysis
  • Vulnerability scanning
  • Penetration testing
  • Open-source licensing review
  • Final security review
  • Final privacy review
  • Customer engagement framework

Deliverables

  • Updated policy compliance analysis
  • Security testing reports
  • Remediation report
  • Open-source licensing review report
  • Final security and privacy review reports
  • Customer engagement framework
Penetration testing and vulnerability scanning live here, not A4 — A4 is about executing the security test plan, A5 adds these final, ship-gate-specific checks.
PRS Post-Release Support

Ongoing maintenance and response — the only phase with no single "gate," since it runs for the life of the product.

Deliverables

  • External vulnerability disclosure response process
  • Post-release certifications
  • Third-party security reviews
  • Security strategy for legacy code, M&A, and EOL plans

High-Risk Confusion Zones

These are the same term or activity reappearing across multiple phases with a different purpose each time. This is where most missed questions come from — the fix is always the same: identify the phase context, not just the activity name.

HIGH RISK Threat Modeling
PhaseWhat's happening
A2Initial modeling — DFD created, STRIDE/DREAD first pass
A3Updated artifacts — same model, revised as design solidifies

Separately: don't confuse the tool questions (STRIDE vs. PASTA vs. DREAD) with the phase questions above — they test different things. See the Frameworks section.

HIGH RISK Policy Compliance Analysis
PhaseWhat's happening
A2Initial analysis
A3Updates, as design decisions are made
A4Compliance review, against executed tests
A5Final analysis, gating the ship decision

Same deliverable name in all four phases — the exam relies on you tracking which stage of maturity it's in.

HIGH RISK Security Testing
PhaseWhat's happening
A3Test planning — writing the plan, not running it
A4Test execution — running the plan, producing results
A5Final testing — pen testing & vulnerability scanning specifically

Verb tense is the tell: "developing/documenting" → A3. "Executing/running" → A4. "Penetration test/vulnerability scan" → A5.

Framework Reference

The five core frameworks, plus three supplementary models worth knowing for comparison questions.

FrameworkPurposeKey Differentiator
STRIDEThreat categorizationSpoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege
PASTAThreat modeling process7-stage Process for Attack Simulation and Threat Analysis, tied to business risk
DREADRisk scoringDamage, Reproducibility, Exploitability, Affected users, Discoverability (ternary scale: High=3, Med=2, Low=1)
BSIMMMaturity assessmentDescriptive — studies real-world security initiatives
SAMMPrescriptive frameworkPrescriptive — Software Assurance Maturity Model, a target roadmap

Supplementary models (useful for "which framework does X" comparison questions):

ModelStructure
Microsoft TM4 steps: Diagram → Identify → Mitigate → Validate
OCTAVE3 phases: (1) Asset-based threat profiles, (2) Infrastructure vulnerabilities, (3) Security strategy
TRIKE3 models: Requirements, Implementation, Risk
DREAD scoring bands: 13–15 High · 8–12 Medium · 5–7 Low. PASTA's design-flaw analysis specifically happens in stage 5 (Vulnerability and Weakness Analysis).

Critical Terminology

SDL vs SDLCSDL = Security Development Lifecycle. SDLC = Software Development Lifecycle. SDL is the security layer added on top of SDLC.
CIAConfidentiality, Integrity, Availability — not the intelligence agency.
DFDData Flow Diagram — the core threat-modeling artifact created in A2.
PSIRTProduct Security Incident Response Team — handles post-release vulnerability disclosures.
SAST vs DASTStatic (code, not running) vs. Dynamic (running application) Application Security Testing.
CVECommon Vulnerabilities and Exposures — the naming system for publicly known flaws.
RBACRole-Based Access Control — permissions tied to a role, not an individual.
MFAMulti-Factor Authentication — a second proof of identity beyond a password.
CSRFCross-Site Request Forgery — tricking an authenticated browser into submitting an unwanted request.
XSSCross-Site Scripting — injecting a script that executes in another user's browser.

Exam Success Strategy

When a question names an activity, run it through this checklist before answering:

1
Phase context
Same activity name, different phase = different purpose. Which phase is described?
2
Verb tense
Planning vs. executing vs. reviewing are three different phases even for the same deliverable.
3
Scope indicators
"Initial," "updated," and "final" map directly to A2, A3, and A5 respectively for most recurring deliverables.
4
Role-specific responsibility
Who does what — architect designs, champion promotes, Scrum Master facilitates, developer implements.
5
Sequential dependencies
What has to be true to exit the current phase and enter the next one?
